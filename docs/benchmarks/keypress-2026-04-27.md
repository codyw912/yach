# Live Terminal Idle Keypress Baseline — 2026-04-27

## Summary

This report records the first live Crossterm terminal draw/flush measurement for idle keypress responsiveness. It measures repeated synthetic app keypresses after initial backend-ready state and an initial live terminal render.

**Measurement class:** live terminal.

This is closer to PRD-facing keypress-to-paint evidence than headless proxy measurements because it includes live ratatui rendering through `CrosstermBackend` and terminal draw/flush. It is still synthetic: it injects keys directly into app logic rather than measuring OS keyboard event delivery through crossterm's event stream.

```text
samples=1000
```

## Timing boundaries

Before timed samples, the harness:

1. enters raw mode and alternate screen;
2. creates a live `CrosstermBackend` terminal;
3. creates `BenchmarkApp`;
4. applies synthetic connected and backend-ready state;
5. performs one initial live terminal render.

Each timed sample starts immediately before applying a synthetic character key to the app and stops after rendering/flushing the updated app state to the live Crossterm terminal.

Included:

- prompt mutation through the same app key handler used by the TUI loop;
- ratatui rendering through `CrosstermBackend`;
- terminal draw/flush work performed by the backend.

Excluded:

- OS keyboard event delivery;
- crossterm event polling latency;
- backend/Pi process work;
- active stream or heavy tool output pressure;
- terminal emulator presentation timing beyond the backend draw/flush boundary.

## Claim supported

This report supports a narrow live-terminal keypress claim:

- On this machine and terminal environment, idle synthetic keypress-to-terminal-draw/flush latency is well below the PRD p95 `<16 ms` idle keypress-to-paint target for this 1,000-sample run.

## Confidence and limitations

- **Confidence:** Useful first live-terminal evidence for idle TUI input/render responsiveness. The 1,000-sample run provides a stronger tail baseline than the initial startup 20-sample run.
- **Limitations:** Keypresses are injected directly into app logic. Real OS input delivery and crossterm event-stream polling remain unmeasured, so this should be described as keypress-handler-to-draw/flush rather than full hardware keypress-to-paint.
- **Scope:** Idle only. Active stream and heavy tool output live-terminal keypress measurements remain unmeasured.

## Active-stream follow-up

## Heavy-output follow-up

A third live-terminal sampler measured keypress-handler-to-draw/flush after a synthetic 1 MiB tool result was summarized into transcript/tool state. This characterizes current compact-summary behavior under heavy tool-output input; it does not measure rendering an expanded full-output pane.

```text
samples=1000
workload=terminal/heavy_output_keypress_to_draw_flush_live count=1000 p50=630.000us p95=1.049ms p99=1.609ms max=2.956ms
```

| Workload | Samples | Fixture / scale | p50 | p95 | p99 | max |
|---|---:|---|---:|---:|---:|---:|
| `terminal/heavy_output_keypress_to_draw_flush_live` | 1,000 | 1 MiB synthetic tool result summarized into transcript/tool state before timed keypress/render samples | 630.000 µs | 1.049 ms | 1.609 ms | 2.956 ms |

This supports a narrow live-terminal heavy-output claim: after the current compact summary representation is in app state, keypress-handler-to-terminal-draw/flush p99 is below the PRD heavy-output p99 `<50 ms` target. It does not prove full-output expansion performance.

Product note: full-output expansion is a high-value future benchmark because large expanded tool output is known to feel slow in Pi during real use. Yach should treat compact-summary performance and expanded-output performance as separate surfaces, not infer one from the other.

## Stream-backlog proxy follow-up

A fourth live-terminal sampler measured a first queue/backlog proxy by including a small burst of synthetic stream events inside each timed sample. Each sample applies 10 prompt-delta backend events, injects one keypress, then renders/flushes to the live terminal.

```text
samples=1000
workload=terminal/stream_backlog_keypress_to_draw_flush_live count=1000 p50=4.027ms p95=16.798ms p99=19.124ms max=20.781ms
```

| Workload | Samples | Fixture / scale | p50 | p95 | p99 | max |
|---|---:|---|---:|---:|---:|---:|
| `terminal/stream_backlog_keypress_to_draw_flush_live` | 1,000 | 10 prompt-delta backend events applied inside each timed keypress/render sample | 4.027 ms | 16.798 ms | 19.124 ms | 20.781 ms |

This is a more demanding active-stream proxy than `terminal/active_stream_keypress_to_draw_flush_live` because stream-event handling is inside the timing boundary. It still is not true async queue contention. The p95 result is below the PRD active-stream p95 `<32 ms` target, but it is close to the 60 Hz frame budget and much slower than the simple active-stream/growing-transcript sampler. This should remain visible as the current best warning signal for stream backlog pressure.

## Async backlog follow-up

A fifth live-terminal sampler measured a true async queue/backlog harness. Unlike the stream-backlog proxy above, this starts an independent producer thread that feeds synthetic prompt-delta backend events into a queue while the UI sampling loop independently drains currently queued events, applies one keypress, and renders/flushes to the live terminal.

The run below was executed through macOS `script` to provide a PTY from the agent shell:

```sh
script -q /dev/null \
  just dev cargo run -p yach-bench --release -- \
    terminal-async-backlog-report --samples 1000
```

```text
samples=1000
workload=terminal/async_backlog_keypress_to_draw_flush_live count=1000 p50=135.375us p95=234.125us p99=356.209us max=1.885ms
async_backlog_profile=baseline events_per_burst=10 producer_sleep_us=500 events_sent=10000 drained=10000 max_drained_per_sample=30
```

| Workload | Samples | Fixture / scale | p50 | p95 | p99 | max |
|---|---:|---|---:|---:|---:|---:|
| `terminal/async_backlog_keypress_to_draw_flush_live` | 1,000 | independent producer thread sends 10 prompt-delta events every 500 µs; each timed sample drains queued events, applies one keypress, and renders/flushes; 10,000/10,000 events drained, max 30 drained in one sample | 135.375 µs | 234.125 µs | 356.209 µs | 1.885 ms |

A higher-rate stress variant sends 50 prompt-delta events every 100 µs:

```text
samples=1000
workload=terminal/async_backlog_stress_keypress_to_draw_flush_live count=1000 p50=164.625us p95=456.292us p99=1.014ms max=2.599ms
async_backlog_profile=stress events_per_burst=50 producer_sleep_us=100 events_sent=50000 drained=50000 max_drained_per_sample=450
```

| Workload | Samples | Fixture / scale | p50 | p95 | p99 | max |
|---|---:|---|---:|---:|---:|---:|
| `terminal/async_backlog_stress_keypress_to_draw_flush_live` | 1,000 | independent producer thread sends 50 prompt-delta events every 100 µs; each timed sample drains queued events, applies one keypress, and renders/flushes; 50,000/50,000 events drained, max 450 drained in one sample | 164.625 µs | 456.292 µs | 1.014 ms | 2.599 ms |

This is the first true async queue/backlog harness because backend events arrive independently of the timed keypress samples. It still uses synthetic prompt-delta events and synthetic key injection, and it does not include OS keyboard delivery or crossterm event polling. The current baseline and higher-rate stress results are far below the PRD active-stream p95 `<32 ms` target. The harness records sent/drained event counts and maximum per-sample drain depth; future work should confirm whether these rates reproduce pressure comparable to real streaming sessions.
