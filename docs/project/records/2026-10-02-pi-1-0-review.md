## 1. Core versus extension territory

### The policy, and how it is actually enforced

"We wait until something has proven itself, and only then do we consider
adopting it; weighing its true functionality against its inherent added
complexity" (announcement). The 1.0 additions: Codemode (native MCP plus
non-LLM models), extension virtual models, deferred tool loading, Anthropic
cache warming, mid-conversation system messages, a new TUI theme, fullscreen
by default.

The rule is "core grows where the extension seam was missing". The MCP post
says MCP "could have been an extension, as it was" (`pi-mcp-adapter`); it moved
in because proper support needed tool-loadout changes (deferred, codemode-only)
that were "generally useful" and that an extension could not get from core
metadata. The shipped result is still extension-shaped: `codemode`,
`tool-search`, `mcp`, `llama.cpp` are built-in *extensions*, and three are
`replaceable` (`coding-agent/src/extensions/index.ts:7-13`); an extension that
registers `/mcp`, `codemode`, or `tool_search` displaces the built-in
(`coding-agent/docs/mcp.md:262-266`). Pi's minimalism is enforced by dogfooding
its own extension API.

Left out of core: approvals and sandboxing ("does not ask for approval before
every tool call", `coding-agent/docs/security.md:3`), subagents, plan mode.
Skills and prompt templates are on-demand text (`coding-agent/docs/skills.md:3`).

### The added features

**Codemode.** One tool taking raw JavaScript, run in a QuickJS-wasm VM per
script with no Node, filesystem, network, or timers
(`coding-agent/docs/codemode.md:3,7`; `codemode/src/wasm.ts:5-22`;
`codemode/src/runtime/host.ts`). Scripts call other tools as `tools.<name>()`
through `ctx.executeTool()`, so calls pass validation and the extension
`tool_call`/`tool_result` handlers and carry `parentToolCallId`
(`coding-agent/docs/extensions.md:148`; `.../codemode/execute.ts:363`;
`mcp.md:250`). Only script output reaches the model. Globals include BM25
`searchTools()`, `describeTool()`, branch-scoped `store()/load()` persisted as
`codemode-store` session entries (`codemode.md:55`), and `models`:
`classify()` (typed `choice|score|bool` questions with probabilities; the Jev
surface) and `generateImages()`, four concurrent, usage added to session cost
(`codemode.md:59-92`). Output defaults to 10k tokens with the full text spilled
to a temp file; VM memory 256 MB (`codemode.md:15,205`). Declarations share a
3000-token budget (`codemode.md:49`); 1.0 cut codemode's prompt ~40%
(`coding-agent/CHANGELOG.md:31,51`). **Yach: absent.** `crates/` and `docs/`
contain no sandbox host. **By-design-different intent:** owner preference
2026-07-31 is that code mode "belongs in an extension, not in core", with calls
routed through yach's executor so review gating and the sensitive-path
chokepoint still apply
(`docs/project/specs/2026-07-31-rig-upgrade-own-the-loop-design.md:146-188`).
Pi's `ctx.executeTool` is the same shape. The spec's open problem, per-call
review inside one script, is not solved by Pi, which has no approvals.

**Native MCP.** stdio and streamable HTTP with OAuth, user and trust-gated
project config (`mcp.md:30-64,115-187`). Per-tool `exposure`: `codemode`
(default: callable from scripts, not declared), `deferred`, `direct`, `hidden`
(`mcp.md:189-200`; `coding-agent/src/core/extensions/types.ts:509`). Server
annotations (`readOnlyHint`, `destructiveHint`) reach permission extensions
(`mcp.md:252`; `extensions.md:166-178`). **Yach: absent**, by intent: the
capability contract exists so an MCP client *can* be an extension
(`docs/project/specs/2026-09-16-extension-capability-contract-design.md`,
Motivation).

**Deferred tool loading.** Three layers. Exposure: `deferred` tools are
undeclared; `tool_search` BM25-ranks them and calls `setActiveTools()`
(`.../tool-search/tool.ts:1-9,209`). Transcript: the load is recorded as a tool
change and survives resume, `/tree`, fork (`mcp.md:226`; `CHANGELOG.md:66`).
Provider: on Anthropic, tool changes go out as native `tool_addition` /
`tool_removal` blocks (beta `inline-tools-2026-09-15`,
`ai/src/api/anthropic-messages.ts:195,1337-1352`), with a never-active
`defer_loading` placeholder declared from request one because the first tool
change otherwise "measured: full miss" (`anthropic-messages.ts:197-209`).
**Yach: absent.** A fixed 7-tool roster is computed per request
(`crates/yach-backend/src/runner.rs:4154-4161`); the playbook review already
says roster changes invalidate provider caches and should be measured first.

**Mid-conversation system messages.** `SystemMessage` is a transcript entry:
leading = prompt; later ones carry added `content`, named `sections`
(replace, or `null` removes), `toolsAdded`/`toolsRemoved`
(`ai/src/types.ts:512-538`). Replaying them in order yields the current prompt
and tools (`ai/src/utils/transcript.ts:73-96`); before each request the agent
loop diffs executable tools against the declared set and inserts the delta
(`agent/src/agent-loop.ts:324-363`). Models with
`supportsMidConvoSystemMessages` (`types.ts:945`) get messages in place; others
get the transcript collapsed to one leading message (`transcript.ts:104-119`).
For Anthropic, updates are held until just before the next assistant message so
`tool_result` still follows `tool_use` (`anthropic-messages.ts:1319-1327`).
Extensions change prompt *sections* and tools, not raw text (`extensions.md:103`).
Effect: prompt and tool changes become journaled transcript state and
cache-preserving appends. **Yach: absent.** Yach rebuilds a flat message list
from the log each turn with one leading baseline-guidance message
(`runner.rs:3927-3939`); static context is re-read per request by accepted spec
(`2026-05-13-native-static-context-design.md:131-136`, as cited in the playbook
review). The playbook's `SessionState = fold(events)` candidate heads the same
direction.

**Cache warming.** `CacheWarmer` re-sends the exact last request with
`maxTokens: 1` before the cache entry expires (`coding-agent/src/core/cache-warmer.ts:284-298,332-339`;
started per request, `core/sdk.ts:404`). Delay is 90% of TTL with a 10 s margin
(`:28-32`). TTL comes from catalog `promptCache: {short, long}`; models without
it are ineligible (`coding-agent/docs/models.md:93-99`). Gate:
`P(continue) × missCost − warmCost ≥ $0.05` (`:20,378-399`), with P=1 while a run
streams and a measured constant 0.15 when idle (`:21-26`). Default mode is
`streaming`; `idle` is opt-in; age caps 30 min idle, 1 h otherwise (`:15-18`;
`settings.md:19-21`). Replay is skipped when budget-based thinking would change
the cache key (`:48-58`). Cost lands as a `usage` session entry, not in model
context; `/session` shows the next decision; extensions can override via
`cache_warming_decision` (`extensions.md:119-121`). **Yach: partial at best.**
Catalog has `cache_read`/`cache_write` prices (`crates/yach-catalog/src/lib.rs:60-61`)
and vendored rig `Usage` has `cached_input_tokens` and
`cache_creation_input_tokens` (`vendor/rig-core/src/completion/request.rs:269-272`),
but `ProviderUsage` holds only input/output/total (`provider.rs:297-301`) and
`provider_usage_from_rig` drops the cache fields (`rig_adapter.rs:1502-1519`).
Yach cannot yet see a cache miss. That is YACH-16's visibility half; warming
depends on it.

**Virtual models.** `registerVirtualModel({provider,id,thinkingLevels,route})`;
`route(request, ctx)` runs before every request and returns a physical
`{model, thinkingLevel}` plus optional JSON `state` stored on the session
branch (`virtual-models.md:33-53,88-107`; `core/virtual-models.ts:101`).
`request.reason` is `user | continuation | retry | direct`, so routers can stay
sticky within a turn and keep caches valid (`virtual-models.md:77-84`).
Selection (`model_change`) and dispatch (provider/model on each assistant
message) are recorded separately (`virtual-models.md:18-25`); providers only
see physical models. The shipped `examples/extensions/jev-router.ts` plans on a
strong model chosen by Jev, then switches once (`virtual-models.md:112-114`).
**Yach: absent**; the posture spec defers model roles/tags
(`2026-08-19-extension-first-product-posture-design.md`, Additive
contributions). Jev differs: yach's crate is an approval *reviewer*
(`crates/yach-jev-reviewer/src/main.rs`, `yach.review.v1`); Pi uses Jev as a
classifier for scripts and routing.

**Yach's own bundle vs Pi.** Hashline: **has** (`crates/yach-hashline-extension`,
975 lines, coordinated read+edit replacement); Pi has no equivalent. Presets:
**partial/by-design-different** (`full`/`minimal` component sets,
`2026-09-27-distribution-presets-design.md`) versus Pi's `defaultTools`,
`--tools`, and built-in extension toggles; same intent. Skills: Pi implements the
Agent Skills spec (`skills.md:3,9`); YACH-14 targets the same format and is
unshipped.

## 2. Extension API surface

Pi extensions are in-process TypeScript via `jiti` with the process's full
permissions (`extensions.md:3-5`). The integration table (`extensions.md:73-86`)
covers lifecycle events, tools, slash commands, shortcuts and flags, user and
custom messages, non-context session entries (`appendEntry`), active
tools/model/thinking level, providers, MCP servers, virtual models, renderers
and `ctx.ui`, and inter-extension events. `types.ts` declares 32 `on()` events
including `before_agent_start`, `context`, `before_provider_headers`,
`provider_stream_event`, `tool_call` (mutate/block), `tool_result` (chained),
`turn_end`/`agent_before_settle` (propose entries, request continuation),
`user_bash`, `input`, `session_tree`, `session_compact`. Tools may declare
`exposure`, `namespace`, `annotations`, `outputSchema`, `prepareLoadout`
(`extensions.md:134-180`). UI: dialogs, widgets, header/footer/editor
replacement, overlays, custom components (`tui.md:7-16`); themes list/load/set
(`types.ts:287-293`). State rides tool-result `details`, `appendEntry`, and
branch reconstruction via `getBranch()` (`extensions.md:220-231`).

Yach's surface is a small, out-of-process, versioned protocol. Manifest
`contributes`: tools, static context, replacement bundles, one reviewer
(`crates/yach-backend/src/extension.rs:68-73`). Host stdio-JSONL: inbound
`extension.initialize`, `tool.invoke`, `resource.result`, `review.assess`;
outbound `extension.ready`, `tool.register`, `resource.request`,
`tool.edit_proposal`, `tool.result`, `review.ready` (`extension.rs:331-352,1725-1760`).
The only resource operation is `ReadTextFile` (`extension.rs:262-264`). Five
declared risks (`extension.rs:101-111`) are consented before spawn but not
sandbox-enforced (capability spec, "What this contract is, and what it is
not"). `Capability::ThemeLoading` is defined and unconsumed
(`crates/yach-proto/src/lib.rs:32,1442-1445`). No hooks, commands, providers,
models, status entries, or UI (posture spec, "Current yach boundary").

Gaps that block a real external extension, ranked by my judgment:

1. **No journaled extension state.** Pi has `appendEntry` plus branch
   reconstruction. Yach has none (playbook review, State table). Every
   stateful extension (router, cache policy) hits this first.
2. **No tool-result transform.** Designed in the posture spec, no protocol.
   Pi's chained `tool_result` is the precedent.
3. **No kernel-tool execution from an extension** (`ctx.executeTool`). Needed by
   code mode and MCP-as-extension; the resource channel only reads files.
4. **No tool exposure/deferred class.** Without it an MCP extension floods every
   request.
5. **No command, model, or provider contribution.** Pi's 1.0 story rests on
   virtual models and providers.
6. **No theme contribution.** Deferred by the in-progress theming spec (YACH-20).

Trade-off: Pi buys power with zero isolation; yach's process-hosted model is
what makes a policy kernel meaningful. `[INFERENCE]` The existing
`tool.edit_proposal` pattern (extension proposes, kernel reviews and applies)
is the template for each new surface.

## 3. TUI: fullscreen, theme, and yach's inline bugs

**What fullscreen is.** Two renderers, chosen by `tuiMode` (`regular |
fullscreen`, default fullscreen; `settings.md:94`; `.../tui-renderer.ts:19-49`).
`TuiAltScreen` enters the alternate screen (`\x1b[?1049h`,
`tui/src/tui-alt-screen.ts:63,378`), enables SGR mouse, and owns the viewport.
Layout is a constrained `VStack/HStack/ScrollView` tree: a `ScrollView` with
`follow: "end"` holds the transcript; a fixed dock holds pending messages,
status, widgets, editor (`minSize: 3`), footer, each `shrink: 1`
(`.../chat-viewport.ts:19-45`). `TuiMainScreen` is the old differential
renderer into terminal scrollback, kept as `regular` (`tui-main-screen.ts:124`).
On exit fullscreen prints the whole logical document to normal scrollback
(`tui-alt-screen.ts:397-420`; `fullscreenExitOutput`, `settings.md:95`).

**Not virtualized.** `ScrollView.render` renders the full child and layout clips
it (`tui/src/components/scroll-view.ts:215-219`). The plan lists virtualization
as a future use and a first-implementation non-goal (`tui-plan.md:99,108`) and
relies on per-component render caches (`:21`). 1.0 fixed "memory retained per
rendered message" (`CHANGELOG.md:70`).

**Why.** Capability, not a bug story: in main-screen mode the terminal owns
scrolling, so the app cannot give sticky rows, nested scroll regions, panes,
mouse hit-testing of scrolled-out content, or repaint of off-screen regions
(`tui-plan.md:26-36`). Also: hiding queue/working state while reading old output
"would be surprising" (`:72`); usage doc: editor and status "fixed while the
transcript scrolls" (`docs/usage.md:86`). The announcement gives no further
rationale `[INFERENCE]`. Costs are acknowledged: mouse capture changes native
selection and link hover (`tui.md:56-62`; `terminal-setup.md:29-67`), and Pi
ships its own selection, copy, search, scrollbar, wheel acceleration
(`settings.md:94-98`; `keybindings.md:98-117`).

**Bearing on yach.** Yach uses ratatui `Viewport::Inline(terminal rows)`
(`crates/yach-ui/src/app.rs:4234-4240`) and archives finished turns with
`insert_before` only when the *next* prompt is sent (`app.rs:3605-3610,3613-3621,4296-4303`);
layout is transcript `Min(1)`, composer, status (`yach-ui/src/layout.rs:32-53`).

- *Blank gap after reply.* `[INFERENCE]` consistent with a full-height inline
  viewport whose transcript area is only partly filled because completed turns
  stay live in the viewport until the next prompt. Not reproduced here; the
  `TuiGapFix` worktree owns the diagnosis. Pi avoids the class in fullscreen
  (viewport = screen, follow-end) and in `regular` by append-only document
  rendering.
- *Large approval prompt shows earliest lines.* `[INFERENCE]` a leaf taller than
  its allotment is clipped from the top. Pi's leaf layout handles exactly this
  in one place: when rendered lines exceed the allocated height it offsets so
  the line holding the cursor marker is visible (`tui/src/layout.ts:120-124`).
  The transferable part is the rule (clip to keep focus/latest visible; give
  the dock `shrink`/`minSize`), not fullscreen.

Fullscreen would not fix yach's bugs without also adopting Pi's costs (owned
scroll, selection, search, mouse). Pi still ships `regular`, which is evidence
scrollback-native users persist. `[INFERENCE]` Fixing inline is cheaper than
copying fullscreen.

**Theme.** Built-ins are `system` (default, generated), `dark`, `light`
(`themes.md:3-7`).

- *Token model.* JSON with `name`, optional `appearance`, `vars`, `colors`;
  51 required roles (`theme-schema.json`), named for interface roles not
  components: `accent`, `border*`, `muted`, `userMessage*`, `toolPendingBg`/
  `SuccessBg`/`ErrorBg`, `toolTitle`, `toolOutput`, `md*`, `toolDiff*`,
  `syntax*`, thinking levels (`themes.md:104-128`). Color forms: hex, OKLCH,
  OKHSL, 256-index, variable, `""` = terminal default (`themes.md:81-92`).
  Components apply `theme.fg/bg/style({fg,bg,bold})` (`tui.md:80-98`).
- *`system`.* Queries terminal fg/bg and the 16 ANSI colors (100 ms cap), takes
  each token's hue from an ANSI slot and solves lightness for contrast (body
  text ≥ 4.5:1 on background and panels), re-queries on appearance change; with
  no reply it falls back to ANSI indices with no panel backgrounds
  (`themes.md:7-22`; `.../theme/system-theme.ts:1-24`).
- *Light/dark.* `"light/dark"` pair; detection: terminal colors, terminal
  notification, `COLORFGBG`, then dark (`themes.md:40-48`).
- *Extension control.* Extensions get the theme in callbacks and
  `getAllThemes/getTheme/setTheme` (`types.ts:287-293`); themes ship in packages
  and `.pi/themes` after trust (`themes.md:130-136`).
- Pi's `dark.json` still has `toolSuccessBg` `okhsl(158 46% 25%)`, the same shape
  as YACH-19's complaint; Pi avoids it by making `system` the default.

**Yach: partial.** Role tokens exist (`crates/yach-ui/src/theme.rs`), one
`pi_dark` default, no light or `NO_COLOR` path, theme loading unnegotiated. The
theming spec in progress covers this; its non-goals (no OKHSL, no live reload)
keep Pi's useful core: roles, a terminal-relative `system` theme, light/dark
detection.

## 4. Pi Durable

Pi Durable (`packages/durable`, ~15k lines without tests) is a separate
experimental framework, not the coding agent: storage plus a runtime where every
step is a task that checkpoints before moving on, so a new process opening the
same storage resumes unfinished tasks. Cut-off model requests are re-sent with
the partial answer kept and marked aborted; cut-off tool calls rerun only if the
tool declares `replay: "safe"`, otherwise the model is told it was interrupted;
`requestId` gives exactly-once submission; forks share parent history without
copying; compaction is a background task applied at a turn boundary; app state
lives in typed documents committed atomically with the transcript; prompt
sections are rebuilt per request and changes are recorded at the transcript
position where they happened (https://earendil.com/posts/pi-durable/;
`durable/src/harness/harness.ts:104-150`). It builds on `chord`, a plugin/facet
runtime (`chord/README.md:1-8`). The coding agent's own durability is unchanged:
JSONL tree sessions, "if the process dies, you look at what happened and tell it
to continue" (post; `how-pi-works.md:25-31`).

For yach it lines up with M2's failure list: crash at any step, exactly-once
resubmit, background versus blocking compaction (yach blocks at 90%,
`2026-07-20-context-compaction-design.md:227`), journaled extension state. The
roadmap excludes daemon and multi-client scope (`roadmap.md:28-29`), so
multiplayer and storage backends are out. `[INFERENCE]` Two ideas transfer to a
single-process agent: per-tool replay-safety declarations, and prompt changes
journaled where they occurred.

## 5. Codemode and the "no MCP" stance

Pi's position: MCP's weakness is composition; fix it with a harness-side
JavaScript sandbox plus discovery, so schemas cost no tokens and big results are
filtered before the model sees them. MCP tools default to codemode-only
(`mcp.md:195`); the prompt carries a one-line-per-server summary appended as a
delta when it changes so earlier messages stay cached (`mcp.md:202`). Codemode
state lives in the transcript, and it runs where the harness runs, unlike bash
(post, "What Is Codemode?"). The reversal is hedged: MCP is still replaceable by
an extension.

Implications for yach:

- Yach's accepted position (code mode as an extension routed through the policy
  layer) is the architecture Pi shipped, minus Pi's in-process first-party
  trust. It needs a seam that does not exist: an extension executing kernel
  tools under policy (gap 3).
- Codemode works in Pi because nothing gates tool calls. In yach each nested call
  is a reviewable action, and per-call review is the wrong texture for scripts.
  Pi's `annotations` plus a permission extension is the nearest precedent; the
  capability set (YACH-10) is yach's analogue. This is the real design cost and
  Pi gives no answer to it.
- MCP-as-extension is blocked on exposure/deferral; `UsesNetwork`/`RunsProcess`
  declarations are in the capability contract.
- Jev as classifier-in-scripts (Pi) and Jev as approval reviewer (yach) are
  different bets and do not conflict.

## Findings

1. earendil-works/pi is badlogic/pi-mono renamed; same HEAD `69f0be6f`.
2. Pi's minimalism is carried by a replaceable built-in extension layer.
3. Everything added in 1.0 serves one goal: keep the prompt prefix stable and
   push scale into discovery (deferred tools, system-message deltas, cache
   warming, codemode's schema budget).
4. Pi has no approval or sandbox story. Yach cannot copy its codemode or
   extension power without a policy seam Pi never needed.
5. Yach's nearest gaps are session-visible state (extension state, cache
   accounting, journaled prompt/tool deltas), not missing features.
